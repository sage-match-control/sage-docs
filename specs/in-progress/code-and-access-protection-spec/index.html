    Spec — code and access protection¶

    Status: in progress. Sections 2–8 are a to-do list, not a design: each item says what to change and where, and leaves the details to whoever builds it, ordered by value. §3 and §4 are not done, by the owner's decision. §9 (facility workbooks closed to link access) and §10 (two fixes to the played and series rules) are full designs, written to be built without other context. Written 2026-10-11; §9 and §10 added 2026-10-12. Everything to do here is free; §11 records what would cost money. Each section is independent and can be done on its own.

    Built (2026-10-12): §10 (sage-tools-api 3.1.1 and the site's parity case), §9.6 (3.2.0), §9.7 (3.3.0), §9.8 and §9.9 (the site's attendance view, its harness and runbook, and these docs), and §8's LICENSE files. §9.6 assumes the spike's answers are both no (§9.4). Deployed: all of the above is live. 3.1.1–3.3.0 are part of sage-tools-api 3.4.0, which Cloud Run runs (its X-App-Version read 3.4.0 on 2026-10-18), and the site's attendance view is on main. So the running service reads as its service account before S1 has answered. Not done: the owner's tasks in §9.4 (S1, O1, O2, O3), and the Google, GitHub and Cloud settings of §2, §5, §6 and §7. §9.6–§9.9 are done when the first event built after them runs with Restricted workbooks; the spec then moves to implemented/. §9.10 records where the build departs from the design.

    This page is public. It states the rules to follow, not which of them are broken today: check each one when you pick it up.

    1. What is protected, and what cannot be¶

    The code worth protecting runs on the server: sage-tools-api (sync, auth, score and attendance writes, the scoresheet pipeline and the Apps Script) is a private repo. Keep it that way.

    Anything a browser runs (lib/v1/, the tools, Control Center) is readable by whoever opens the page, whatever repo it comes from. So:

    • No obfuscation or minification of the site. It is reversed with free tools, costs a build step the site deliberately does not have, breaks the comparison harness and the lib/v1 compatibility rule, slows pages on venue Wi-Fi and makes event-day debugging harder.
    • The Bracket Generator's draw stays in the browser on purpose. Its verifiable draw (spec) depends on anyone being able to re-run it.
    • The pages and the engine stay in the browser. They render live from snapshots, and the rules they hold are tournament rules players should see.
    • Control Center stays as it is. It holds no secret and enforces nothing itself; the API decides every action.

    Protection is therefore about access: who can edit the workbooks, who can push, what a leaked credential can do, and what an attacker can cost us.

    2. Workbook sharing (Google Drive)¶

    Workbook IDs are public: the masters' IDs are in the Tournament Calculator and every facility workbook's is in event-data/config/events.json.

    • Every link-shared workbook is "Anyone with the link: Viewer", never Editor. That covers both masters (SAGE Dual Meet Master, SAGE Standard Tournament Master) and the facility workbooks of the events registered before §9 shipped (BKL Cup, PNF x BUP, Pickle for Sight, Piggleball, PickleDrive), finished events included. Staff who edit are added by name. The calculator's handoff still works: Make a copy needs only view access. The facility workbooks of newer events are Restricted: §9.
    • Why it matters: an editor can change scores (the onEdit sync publishes them), change the bound Apps Script that every future workbook is copied from, and read Script Properties, where sheets-sync.gs keeps the sync secret.
    • If a workbook holding the secret was ever editor-shared: run SAGE → Replace shared secret in it, and if exposure can't be ruled out rotate SYNC_SHARED_SECRET in Cloud Run (every syncing workbook then needs the new one, so never close to an event).
    • Add it to the dry-run checklist (_templates/dry-run-checklist-template.md): check each facility workbook's sharing before the event.

    A facility workbook goes further than Viewer, to Restricted, once the readers that relied on link access read as the service account: that is §9.

    3. Cloud Run cost cap: not done¶

    No --max-instances cap and no budget alert. Owner's decision, 2026-10-12.

    4. Sign-in rate limiting: not done¶

    POST /v3/sessions and POST /auth/login stay unthrottled. Owner's decision, 2026-10-12.

    5. GitHub settings¶

    Org sage-match-control, on the free organization plan. Only what that plan includes, so none of this costs anything:

    • Require two-factor authentication for members. Every plan has it.
    • Dependabot alerts on every repo, private ones included: free on every plan. On a private repo, turn on the dependency graph first; it is off by default there.
    • Secret scanning with push protection on the public repos only: the site, event-data, and sage-docs while it is public. It is free on public repos. On a private repo it needs GitHub Secret Protection, a paid add-on sold only with GitHub Team, so sage-tools-api goes without it (§11).
    • A ruleset on main (no force-push, no deletion) of the public repos: the site and event-data. On the free plan a ruleset or branch protection is enforced only on a public repo, so sage-tools-api's main, where a push deploys to production, has none (§11). Its protection is who has write access, below, and the pre-push hook (which --no-verify skips).
    • Review who has write access to each repo, sage-tools-api first.

    A repo made private (§7) loses its free secret scanning and ruleset with it.

    6. Least-privilege credentials¶

    • GITHUB_TOKEN (Cloud Run) is a fine-grained token: repository event-data only, Contents read/write, nothing else, with an expiry date and a calendar reminder to renew it outside event weeks.
    • The sage-tools-api-runtime service account is an Editor on facility workbooks (every event's, §9.3 D3), never on the masters.
    • GOOGLE_SHEETS_API_KEY is restricted to the Sheets API in the Google Cloud console.

    7. Where the docs live¶

    sage-docs is public and published to GitHub Pages, so the architecture, auth design and API are readable by anyone. GitHub Pages on a private repo needs a paid plan. Owner's decision, one of:

    1. Leave it public (no cost, no change).
    2. Make the repo private and host the site on Cloudflare Pages (free from a private repo; the account already exists for sage-live). The site URL changes, so every link to sage-match-control.github.io/sage-docs/ has to follow.
    3. Split it: publish features/ and usage/, keep technical/ and specs/ in a private repo.

    8. Licence notice¶

    Add a LICENSE file (all rights reserved, no permission to copy or reuse) to each public repo: sage-match-control.github.io, event-data and, if it stays public, sage-docs. Unlicensed code is already all rights reserved; the file makes that explicit.

    9. Facility workbooks closed to link access¶

    Unlike §2–§8, this section is a full design with build steps, written so it can be built by someone with no other context. §9.1–§9.3 say what and why; §9.4 is what the owner does by hand; §9.5–§9.9 are the build, in the order it ships.

    9.1 Goal¶

    A facility workbook's General access is Restricted. It is shared by name with the people who edit it and with the API's service account, sage-tools-api-runtime@sage-tools-api.iam.gserviceaccount.com. Nobody else can open it, so its ATTENDANCE tab (names, teams, shirt sizes, who is present) and every tab the sync does not publish stay inside the workbook. What the sync publishes to event-data stays public, as now.

    This applies to events built after §9.6–§9.9 ship. It changes nothing for an event already registered (§9.3, D4).

    9.2 What reads a workbook today¶

    Four readers need link access. An API key can read only a sheet that anyone with the link can open, and so can a request with no credential, so all four change:

    # Reader File How it reads now
    R1 The sync's default fetcher sage-tools-api/src/clients/SheetsCsvFetcher.mjs Sheets API values:batchGet, ?key= GOOGLE_SHEETS_API_KEY
    R2 The sync's fallback, { method: "csv" } sage-tools-api/src/clients/GvizCsvFetcher.mjs the gviz CSV export, no credential
    R3 Attendance and score-entry reads sage-tools-api/src/clients/SheetsClient.mjs: readValues, readScoreNotes Sheets API, ?key=. Its writes already send the service account's bearer token
    R4 The desk page and Control Center's Attendance tab sage-match-control.github.io/lib/v1/views/attendance-view.js: attendanceCsvUrl, fetchFacility the gviz CSV export of ATTENDANCE, from the browser, every ATTENDANCE_POLL_MS (10 s, lib/v1/platform.js)

    Not affected: the Apps Script (sheets-sync.gs, the two generators), which runs inside the workbook; every page's reading of event-data; the masters.

    The service account's token comes from src/clients/GoogleAccessToken.mjs: token() fetches it from Cloud Run's metadata server with the spreadsheets scope (reads included) and caches it; GOOGLE_ACCESS_TOKEN overrides it for local runs; email() gives the account's address for messages. It is constructed once in src/app.mjs (googleAccessToken).

    9.3 Decisions¶

    Decision Consequence
    D1 GOOGLE_SHEETS_API_KEY stays, as a fallback. Reads use the token. The key is used when no token can be had (a local run with no metadata server and no GOOGLE_ACCESS_TOKEN). Whether a 403 to the token is retried once with the key depends on spike S1b (§9.4): only if a token cannot read a link-shared workbook the account was never given, since only then could the key succeed where the token failed.
    D2 The gviz fallback (R2) is kept. If spike S1a (§9.4) shows gviz accepts the service account's bearer token, R2 sends it; if not, R2 stays as it is and works only on a link-shared workbook. Either way the code stays and { method: "csv" } keeps its meaning. The docs say which case holds.
    D3 The service account is Editor on every facility workbook, whatever the event's attendance and scoreEntry settings. One runbook step for every event, and turning attendance or score entry on later needs no re-share. §6 says the same.
    D4 Workbooks of events already registered keep their sharing. BKL Cup, PNF x BUP, Pickle for Sight, Piggleball and PickleDrive are finished. Pages that read their workbooks straight from Google (the archived pages under events/archives/, and the frozen desk pages of Pickle for Sight, Piggleball and PickleDrive) keep working.
    D5 The desk list is read through a new API route, GET /v3/days/{day}/facilities/{facility}/people (§9.7). Taken because R4 is the only reader in a browser, and a browser has no credential Google accepts.
    D6 The list read is cached on the server for 10 s per workbook, shared by every caller, and dropped on every write to that workbook's ATTENDANCE tab. The number of desks open does not multiply reads from Google (§9.4, O2). A marker sees their own change at once; another desk within one poll and one cache period (≤ 20 s).
    D7 Signed out, Control Center's Attendance tab shows a sign-in prompt ("Sign in to see attendance") in place of the list, and fetches nothing. (Owner, 2026-10-12.) Today the tab shows the list to anyone, because it reads the public CSV. That is the exposure §9 removes. The desk page always has its desk token, so it is unaffected.

    9.4 Owner tasks (not code)¶

    These need the Google account and the Cloud console, so the owner does them.

    • S1, the spike: what the service account's own token can read. Two answers are needed before §9.6 starts, and they must come from the service account's token with the spreadsheets scope, which is what the API sends (your own token or an Apps Script token has other scopes and proves nothing). In Cloud Shell (project sage-tools-api):

    • Let yourself mint the account's tokens, once: gcloud iam service-accounts add-iam-policy-binding sage-tools-api-runtime@sage-tools-api.iam.gserviceaccount.com --member="user:<your Google address>" --role=roles/iam.serviceAccountTokenCreator

    • Make two test spreadsheets, each with a tab named T and any text in A1. A: General access Restricted, shared with the service account as Editor. B: General access "Anyone with the link: Viewer", not shared with the service account.
    • Get a token: TOKEN=$(gcloud auth print-access-token --impersonate-service-account=sage-tools-api-runtime@sage-tools-api.iam.gserviceaccount.com --scopes=https://www.googleapis.com/auth/spreadsheets)
    • Check the token works at all: curl -s -H "Authorization: Bearer $TOKEN" "https://sheets.googleapis.com/v4/spreadsheets/<A>/values/T!A1" should show A1's text. If not, fix this before going on.
    • S1a, does gviz take the token? curl -s -H "Authorization: Bearer $TOKEN" "https://docs.google.com/spreadsheets/d/<A>/gviz/tq?tqx=out:csv&sheet=T" | head -3. The A1 text, in quotes, means yes; an HTML page means no.
    • S1b, does the token read a link-shared workbook it was never given? The same Sheets API call as step 4, on B. A1's text means yes; a 403 means no.
    • Remove the binding from step 1 (remove-iam-policy-binding, same arguments) and delete the two spreadsheets.

    Record both answers here, under D1 and D2. S1a decides whether GvizCsvFetcher sends the token (§9.6). S1b decides the 403 retry: if yes, the key can never succeed where the token got 403, so there is no retry; if no, a 403 to the token is retried once with the key, so a finished event's link-shared workbook still reads. - Until S1 is answered, the build assumes both answers are no, the choice that keeps every read working whichever way it turns out: S1b no means retryRefusedWithKey: true in src/app.mjs, and S1a no means GvizCsvFetcher is unchanged and works only on a link-shared workbook. If S1b answers yes, set retryRefusedWithKey to false (a refused workbook then costs one request, not two). If S1a answers yes, GvizCsvFetcher takes the SheetsReadAuth as its second argument and sends the token as §9.6 describes, with the two tests listed there. - O1, the Sheets API quota. In the Google Cloud console (project sage-tools-api), open APIs & Services → Google Sheets API → Quotas and note Read requests per minute per user. Every read moves to one identity, the service account, so this is the limit that counts. At the time of writing Google's documented default is 60 a minute per user (300 per project). - O2, compare it with an event's peak. The reads a minute at one event's busiest moment, with §9.7's cache: - syncs: one batchGet each. On 3 October 2026 two events made 936 syncs in 3 h 15 min, about 5 a minute. - desk lists: at most 6 a minute per facility (one per 10 s cache period), however many desks are open. - marks: one read each (ATTENDANCE!A1:Z), at the rate people arrive. - score entry: two reads per save (SCHEDULE and the score notes). - reconcile after a sync: one or two reads per facility, when the roster changed.

    For three facilities that is roughly 5 + 18 + marks + scores. If the quota is 60 or close to the estimate, request a raise (to 300) on the same page; it is free. Do it before the first Restricted event. - O3, after §9.8 ships: the first event built after it has every facility workbook Restricted and shared with the service account as Editor, from the start. Never change a live event's sharing during its event week.

    9.5 Before you build¶

    Read this whole section, then the workspace CLAUDE.md (the root of D:\Personal\SAGE), which holds every repo's rules. The rules that matter here:

    • sage-tools-api: no production change without a failing test first. Every change to src/ changes test/ in the same commit; run npm test before every commit and npm run verify before every push to main. A push to main deploys to Cloud Run, so never push in an event week. Bump package.json (patch for a fix, minor for a feature) and add a README.md Changelog entry ending with a Tests: line. Only src/app.mjs constructs objects. src/clients/ may import shared/*, domain files and built-ins, never registry/, services, routes or express. Never weaken or delete a test to make a change pass; when a test pins behaviour this section changes on purpose, change it and say so in the commit message.
    • The site: only lib/v1/ is edited, and only compatibly: add, never remove or rename an export, and never change an export's parameters or return shape. views/ may import only domain/ and views/ (so not data/api.js). Run cd _tests && npm install && npm run verify before every push to main; never merge within 3 days of an event.
    • sage-docs: present tense; every change carries its version (see docs/changelog.md, "Releasing a version").

    Release order. At the time of writing sage-tools-api is at 3.1.0; take the next free numbers when you build.

    9.6 Build 1: the server reads as the service account (R1, R2, R3)¶

    sage-tools-api, a minor release. Needs S1's answers.

    A read credential, in one place. Add src/clients/SheetsReadAuth.mjs (PascalCase, like every other file in src/clients/) and its mirrored test, exporting class SheetsReadAuth:

    // constructor({ accessToken, apiKey = null, retryRefusedWithKey = false, logger,
//               now = () => Date.now(), tokenRetryMs = 60_000 })
//   accessToken: a GoogleAccessToken; apiKey: GOOGLE_SHEETS_API_KEY or null;
//   retryRefusedWithKey: true only if S1b answered "no" (§9.4)
//
// async primary() -> { kind: "token", headers: { Authorization: "Bearer …" } }
//                  | { kind: "key",   key: "<api key>" }
//   The token, unless token() failed less than tokenRetryMs ago (remembered,
//   so a local run without a metadata server does not wait 3 s on every read).
//   The key when no token can be had. Throws UpstreamError
//   "Google Sheets: no credential (no service-account token and no
//   GOOGLE_SHEETS_API_KEY)" when neither exists.
//
// fallbackAfter(credential) -> the key credential, when retryRefusedWithKey is
//   true, `credential` was the token and an API key is set; otherwise null.
//
// async refused() -> a SheetsAccessError (below) whose message is
//   "The API can't read this workbook. Share it with <email> as Editor."
//   (email from accessToken.email(), or "the API's service account" when it
//   is unknown)

    A refusal is its own error, so nothing retries it. Add to src/shared/errors.mjs: export class SheetsAccessError extends UpstreamError {}. It keeps UpstreamError's 502 and code: "upstream_failure", so no API answer changes. Add a case to test/unit/shared/errors.test.mjs: it is an UpstreamError, with status 502 and code upstream_failure.

    Every reader then follows the same steps:

    1. const cred = await auth.primary(). A token goes in the Authorization header; a key goes in the key query parameter, as today.
    2. If the answer is 403 and auth.fallbackAfter(cred) is not null, send the same request once more with that key credential.
    3. If the answer is still 403, throw await auth.refused().
    4. Any other status is handled exactly as today.

    Changes:

    • SheetsCsvFetcher (R1): the constructor becomes (logger, auth, timeoutMs), where auth is a SheetsReadAuth. #fetchBothOnce follows the steps in place of url.searchParams.set("key", …), and its "no API key" check goes (it is primary()'s throw now). In #fetchBoth's retry loop, rethrow a SheetsAccessError at once instead of retrying: a refused workbook is refused on every attempt, and retrying would cost six requests and 3 s of sleep per facility per sync. SyncService records any thrown error as that facility's failure and keeps its last published data, as now. The roster tab's 400 Unable to parse range retry is unchanged.
    • SheetsClient (R3): the constructor takes auth (a SheetsReadAuth) in place of apiKey, and keeps accessToken for writes. readValues and readScoreNotes build their URL without key= and send through a private #read(url) that follows the steps, reusing #send's timeout and 429 handling. readValues's 400 Unable to parse range → null stays. Writes are unchanged, including their own 403 message ("can't edit … as Editor").
    • GvizCsvFetcher (R2): only if S1a answered yes. The constructor takes auth as its second argument, and #fetchTextOnce sends the token's Authorization header when primary() gives a token, and nothing when it gives a key (gviz takes no key). If S1a answered no, change only its header comment.
    • GoogleAccessToken.token(): share one in-flight request, so many reads at once on a cold instance ask the metadata server once. Keep the promise while it is pending; drop it when it settles, whether it resolved or rejected.
    • src/app.mjs: construct one SheetsReadAuth next to googleAccessToken, passing retryRefusedWithKey as S1b decided (a literal, with a comment naming this section). Pass it to both SheetsClient constructions (the attendance one and the score-entry one) and to SheetsCsvFetcher (and to GvizCsvFetcher under S1a = yes). Rewrite the comment above googleAccessToken ("Attendance writes …"): the account now reads for the sync, attendance and score entry, and writes for attendance and score entry.
    • Comments to correct: the header of SheetsClient.mjs ("Reads use the API key (the workbooks are link-viewable …)"); the readScoreNotes comment ("A read, so the API key"); GvizCsvFetcher.mjs's header ("needs no API key"): say it works on a link-shared workbook, or also on a Restricted one with the token under S1a = yes; and GoogleAccessToken.mjs's header, which cites only the attendance spec: name everything that uses the token.
    • loadConfig.mjs needs no change: GOOGLE_SHEETS_API_KEY stays optional (D1). In .env.example, say on its line that it is the fallback for reads.
    • src/shared/ports.mjs needs no change: the ports describe the clients' methods, which keep their signatures.

    Tests, written first. Tests build a real SheetsReadAuth around a fake access token, { token: async () => "TOK", email: async () => "sa@example.com" }, or one whose token() rejects. Wherever an existing test or helper passes an API key, pass new SheetsReadAuth({ accessToken: <a rejecting fake>, apiKey: "KEY", logger }): it then reads with the key exactly as today, so those tests keep their meaning.     9.7 Build 2: the attendance list from the API (R4, server half)¶

    sage-tools-api, a minor release.

    The route. In src/attendance/routes.mjs, attendanceV3Routes:

    router.route("/days/:day/facilities/:facility/people")
    .get(auth.requireOperatorOr("desk"), asyncHandler(handlers.listPeople))

    Add listPeople to attendanceHandlers: it calls attendanceService.listPeople({ day: req.params.day, facilityName: req.params.facility, actor: req.actor }), sets Cache-Control: no-store, and answers 200 with the array itself (no envelope, per the API conventions).     The body: a JSON array of people, in sheet order, one per key:

    [
  { "key": "ana-santos", "player": "Ana Santos", "teams": ["PNF_LIWD_1"],
    "categories": ["LIWD"], "present": true, "timeIn": "2026-10-03 08:14",
    "withdrawn": false, "shirt": "M" }
]

    This is the Person shape the site's parseAttendanceCsv (lib/v1/domain/attendance.js) builds today, so the page renders it unchanged. The rules below copy that function's, so the same sheet gives the same list.

    The rules, a new pure function peopleFromTab(values) in src/attendance/domain/attendanceTab.mjs. values is what readValues(sheetId, "ATTENDANCE!A1:Z", { render: "FORMATTED_VALUE" }) returned, so every cell is display text:

    • Layout: pass values.map(r => (r ?? []).slice(0, HEADERS.length)) to the existing parseTab, exactly as mark does, because parseTab requires row 1 to be exactly the seven headers. A wrong header row throws AttendanceLayoutError, a 409 attendance_layout, as a mark does. Use parseTab's rows for the row order, key and the blank-key skip.
    • One person per key: the first row with that key wins.
    • player: the trimmed player text, or the key when it is blank.
    • teams, categories: split on commas, each part trimmed, empty parts dropped.
    • present, withdrawn: true only when the cell's text is exactly TRUE, the site's rule. A checkbox renders as TRUE/FALSE under FORMATTED_VALUE. Do not use parseTab's flag, which also accepts true and so differs from the site.
    • timeIn: the trimmed text.
    • shirt: from the full row 1 (A–Z, not the seven-column slice), take the first name in SHIRT_HEADERS order that some trimmed header equals, and read that column; "" when none does. List order, not column order, is the site's rule: with both Shirt Size and TShirt Size present, TShirt Size wins. Add export const SHIRT_HEADERS = ["TShirt Size", "T-Shirt Size", "Shirt Size", "tshirtSize", "shirtSize"]; to attendanceTab.mjs: the same list, in the same order, as the site's ATTENDANCE_SHIRT_HEADERS, which stays where it is.

    FORMATTED_VALUE (not the mark's UNFORMATTED_VALUE) because the page shows what the sheet displays: a hand-typed time stays text instead of arriving as a date serial number, as it did through gviz.

    The service method, AttendanceService.listPeople({ day, facilityName, actor }), makes exactly mark's checks, in the same order, with the same errors:

    1. config.getDay(day) (an unknown day is a 404 on /v3), then the event's attendance setting: unset → NotFoundError("Attendance is off for this event").

    4. Read and return peopleFromTab(values). A missing tab (readValues gives null) is [], not an error: the page shows "no roster yet", as it does today.

    10.1 Reading a score's value¶

    Both sides count a cell as a score when its trimmed text is not blank and is a number (!isNaN). They read its value differently:

    Reads with 11.5 1e1
    The site: rowsToMatches in lib/v1/domain/matches.js parseInt(raw, 10) 11 1
    The server: unneededSeriesGames in facilityCompletion.mjs Number(raw) 11.5 10

    Only the series-final walk compares values on the server, so that is where they disagree. In a twice-to-beat final (two games, codes X_F_1_(1)/X_F_2_(1) and X_F_1_(2)/X_F_2_(2)), game 1 typed 11.5–11 is a seat-1 win on the server, which decides the series and makes game 2 unneeded, so the facility is complete and completedAt is stamped. On the site it is a tie, game 2 is still needed, and the card says one match left. Score entry writes whole numbers only (src/scores/domain/scoreRequest.mjs), but a score typed into the sheet is not checked.

    The fix: in unneededSeriesGames, replace const s1 = Number(g.score1), s2 = Number(g.score2); with const s1 = parseInt(String(g.score1).trim(), 10), s2 = parseInt(String(g.score2).trim(), 10);. The site's rule wins because it is the value every page shows. hasScore is unchanged.

    Tests, written first:

    • test/unit/sync/domain/facilityCompletion.test.mjs, in the "series finals" describe: unneededSeriesGames with game 1 "11.5"–"11" and game 2 unscored gives an empty set (it gives game 2's key before the fix); and facilityIsComplete on the same two rows as CSV is false.
    • In the site repo, add to CASES in _tests/unit/parity-server.test.mjs:
    'a decimal score in a series final': csvOf(
  row(1, 'X_F_1_(1)', 'a', 'b', '11.5', 'X_F_2_(1)', 'c', 'd', '11'),
  row(2, 'X_F_1_(2)', 'a', 'b', '', 'X_F_2_(2)', 'c', 'd', '')),

    Push it after the server fix is on main: until then the case fails, because it imports the server's file from the sibling checkout.
