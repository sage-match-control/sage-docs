    Spec — Court Control from Control Center¶

    Status: in progress. Built and live on 2026-11-14 (sage-tools-api 3.8.0, the site's lib/v1/ and Control Center, and the docs); the owner's checks K1–K6 (§10.2) on workbook copies are left, and it moves to implemented/ once they pass. Written 2026-10-05 as an outline. Rewritten on 2026-11-14 as a build spec, against sage-tools-api 3.7.1, the site engine (lib/v1/), both workbook generators, and the Court Control tabs of five real workbooks (ACSO and UPAP, standard; PNF x BUP, dual meet; Ladies' Dink and Millennium, team). Every decision is settled (§1). There are no open questions: do not stop to ask about anything §1 covers. §11 (the score dialog's "next match" prompt) is a later phase, outlined only. Do not build it.

    Builds on Score entry from Control Center, whose service account, write path, conflict check and dialog this reuses. Read that spec's §3–§5 before starting. This one assumes them.

    Let a signed-in operator put a match on a court, replace it, or clear the court, from Control Center's Live Matches tab, without opening the facility workbook.

    0. Read this first¶

    This spec is written for an implementer with no other context. Do the sections in order: the API (§4), then the site (§5 to §7), then the docs (§8). Check each part as §9 says. Report as §10 says.

    0.1 The system in one paragraph¶

    Each tournament day has one Google Sheet ("facility workbook") per venue. Operators type into it. An installable onEdit trigger (apps-script/sheets-sync.gs) then asks the Cloud Run service sage-tools-api to re-read the workbook's CSV and STANDINGSCSV tabs and publish a JSON snapshot of the day. Every page reads that snapshot. The pages are the public Tournament Hub, the schedule board, and the operator console Control Center (sage-match-control.github.io/tools/control-center.html). A snapshot is published through a Cloudflare Worker that pushes it to open pages over a WebSocket, and it is archived to GitHub. One tab of the workbook, Court Control, says which match is on which court right now. Its values become each match's court column in CSV. On the site that column is liveCourt, and it is what makes a match show as live everywhere. Today an operator types match numbers into Court Control by hand. This spec lets Control Center write that cell instead, through a new API route.

    3. API: test first. For every production change, write the test, watch it fail, then make it pass (sage-tools-api rule). Never weaken or delete a test to make a change pass.

    0.4 Facts checked against the code and workbooks (2026-11-14)¶

    These are the facts the design rests on. If one is no longer true when you start, stop and report it (§10.1 item 4).

    1. Court Control's shape differs between workbooks. Each court is a 3-row block. Column B holds the court's label, merged over the block's 3 rows. Column C, on the block's first row, holds the match number typed by hand. D and E are formulas that read the match, and with C blank they show #REF! or -. Where the blocks start is not the same everywhere:
    Workbook Header row (Court, Match) First court row B holds
    Standard (ACSO, UPAP; standard-tournament-generator.gs) 4 5 =Variables!R<k+1>, the sidebar's court labels (1, 2, … or 5,6,7…)
    Dual meet (PNF x BUP) 5 6 the court number
    Team (Ladies' Dink, Millennium) 5 6 the court number

    In the Ladies' Dink workbook, courts 7–12 hold the text # in C. Below the courts, B also holds non-court labels with input cells beside them: Next Stand By (row 50), TBA Stand By (53) and Match to Record (56, 59). The PNF workbook has counters in B3:C3 (0, 0). So the API never assumes a row. It finds a court's row by the number in B (§4.3), starting at row 4. 2. The live court is B's value. CSV's court column is FILTER('Court Control'!B:B, 'Court Control'!C:C = matchNumber). On the site, lib/v1/domain/matches.js reads that column as liveCourt. CourtAssignment is the scheduled court, a different field (m.court, such as Court 3). 3. Live Matches keys a court by its number. buildFacilityCourtGroups in lib/v1/views/live-matches.js makes one row per court that appears in the facility's scheduled matches, keyed by the digits of CourtAssignment (courtNumberFrom). It adds any court that has a liveCourt, keyed by that raw value. A court with no scheduled match gets no row. A court whose label has no digit gets a row only while occupied. 4. Three builders draw a court cell, each as one <td class="live-court-cell" …>: liveTableRowsHTML (occupied), liveEmptyRowHTML (idle, class live-court-cell idle) in views/live-matches.js, and liveRowHTML in views/teams.js (a team event's occupied row, which Control Center passes as options.liveRow). Each court's HTML holds exactly one such <td>. 5. Control Center always shows Live Matches. consoleDayIsLive() returns true, so there is no go-live gate. drawLiveMatches() (around line 2309) calls Live.renderLiveMatches(MODEL, {…}) on every new snapshot. scoreDialog.refresh() is called right after it (around line 1595). 6. MATCHES and MODEL.matchesByFacility hold different objects. MATCHES (= model.matches) holds copies that carry facility. matchesByFacility holds the facility's own objects, which have no facility. A fixture-mode patch must update both (§7.4). 7. An API write fires no onEdit. So the API publishes in the same request through syncService.syncDay, as ScoreService.submit does (score entry's D4). 8. Score entry gates on scoreEntryAvailable() in Control Center: the event's scoreEntry is "console" or "links", and the operator is signed in (or FIXTURE is set). It also draws a ✎ Enter score hint (.score-hint). 9. Speed. A score save at ACSO (13 Nov 2026) took 7.0 s typically, most of it the publish. A court write takes the same path without the cell note: about 5 s from Save to the pages updating. A hand edit in the sheet takes about 2–4 s.

    1. Decisions (settled with the owner, 2026-11-14)¶

    # Decision
    D1 Operators only. Only a signed-in operator token may set a court. Scorer and desk tokens get 401. The scorer page gets nothing
    D2 No new switch. Court control is on exactly when score entry is: the event's scoreEntry is "console" or "links" and the event is not archived. Otherwise the API answers 403 court_control_off
    D3 A court is found by the number in its label, its first run of digits ("Court 3" and 3 are court 3). This is the rule Live Matches already keys by. A court whose label has no digit cannot be set from the console
    D4 No GET. The route is a PUT alone, with an exceptions-table row, as the score route has. The published snapshot already carries every live court
    D5 The API refuses, the console warns. The API refuses: an unreadable or unsafe cell (a formula, an error, text), a match not in SCHEDULE, a BYE match, a match already on another court, and a changed cell (409). Everything else is a warning in the dialog, and the operator may go ahead anyway
    D6 Moving a match between courts is two actions: clear the old court, then set the new one. The API never writes two cells in one request
    D7 The button is the court cell. In Live Matches, the court's own cell (the number at the left of the row) is the button, with a small ✎ Set match (idle) or ✎ Change (occupied) label under the number. There is no separate pencil icon. It appears only where score entry would (fact 8)
    D8 Publish in the same request, even when unchanged, as score entry does. A retried save may have written without publishing
    D9 No cell note. The cell is overwritten many times a day. The API logs one court line per request instead
    D10 The score dialog's "Court 3 is free: put #57 on it?" prompt is a later phase (§11). This build does not touch views/score-dialog.js

    3. Finding a court in Court Control¶

    The API reads 'Court Control'!B4:C200 twice, in parallel: once with UNFORMATTED_VALUE, because B is a formula in standard workbooks and only its value is the label, and once with FORMULA, so it can tell what C really holds. Row i of the result (0-based) is sheet row 4 + i. A merged B reads as its value on the block's first row and blank on the other two, so each court has exactly one row.

    • A court row is a row whose B value (as text, trimmed) contains a digit. Its court number is Number of the first run of digits. Court, Next Stand By, Match to Record and blanks are not court rows.
    • The court's row is the one court row whose number equals the requested court. If there is none, the answer is 404. If there are two or more, it is 422 court_layout, naming the rows.
    • The match cell is C on that row, read from the FORMULA result:
    C holds (FORMULA render) Means
    nothing, "", or only spaces empty: null
    a whole number ≥ 1, or text of digits only that match number
    text starting = a formula: refused, 422 court_layout, "Court 3's match cell C14 holds a formula. Set this court in the sheet."
    anything else (#, #REF!, 12a) refused, 422 court_layout, "Court 3's match cell C14 holds "#", not a match number. Set this court in the sheet."
    • "On another court": every other court row whose C (by the same table) is the requested match number. Rows that are not court rows (Next Stand By) are never considered.

    Worked example (team workbook, fact 1): court 3 is row 12. 'Court Control'!C12 is written with 57. In the standard workbook (ACSO), court 3 is row 11.

    Rules:

    4.4 Errors (src/shared/errors.mjs)¶

    Add these classes under a // Court control (src/courts/) heading, after the score-entry errors:

    // The event's scoreEntry setting is absent, or the event is archived (D2).
export class CourtControlOffError extends ForbiddenError {
    constructor() {
        super("Court control is off for this event. It follows the event's score entry setting.");
        this.code = "court_control_off";
    }
}

// Court Control is in a state the API won't write into: no tab, a court number on two
// rows, or a match cell holding a formula, an error or text.
export class CourtLayoutError extends AppError {
    constructor(message) { super(message, 422); this.code = "court_layout"; }
}

// The match can't be put on a court: it isn't in SCHEDULE, or it is a BYE.
export class UnplayableMatchError extends AppError {
    constructor(message) { super(message, 422); this.code = "unplayable_match"; }
}

// The court's cell no longer holds what the client showed. current: { matchNumber }.
export class CourtConflictError extends AppError {
    constructor(current) {
        super("The sheet changed since this court was opened", 409);
        this.code = "court_conflict";
        this.current = current;
        this.extra = { current };
    }
}

// The match is already on another court. onCourt: that court's label.
export class MatchOnCourtError extends AppError {
    constructor(matchNumber, onCourt) {
        super(`Match #${matchNumber} is on Court ${onCourt} now. Clear that court first.`, 409);
        this.code = "match_on_court";
        this.onCourt = onCourt;
        this.extra = { onCourt };
    }
}

    An unknown court is a NotFoundError (404, not_found): "Court Control has no court 3." /v3's error handler already turns all of these into problem details that carry extra. Check that extra reaches the body, as ScoreConflictError's current does, and add it if it doesn't.

    11. Later phase: "Court 3 is free: put #57 on it?" (outline only; do not build)¶

    After a score is saved for a match that is live on a court, the score dialog offers to put the next match on that court in the same step. This is the day's rhythm, "score it, call the next one", in one place. Sketch:

    • A new optional afterSave(state, json) option of createScoreDialog, off by default, so the scorer page is unchanged. Control Center uses it to open the court dialog for that court with courtSuggestions' first match already chosen.
    • No API change: it is the same PUT …/courts/{court}/match.
    • Open questions for when it is specified: whether it opens the court dialog or asks a one-button question in the score dialog's success state, and whether a scored match's court is cleared when the operator declines.

    12. Alternatives considered (do not build these)¶

    • A pencil icon beside the match. It reads as "edit this score", and score entry deliberately keeps Live Matches read-only for scores. It is also a tiny tap target at phone sizes.
    • Exact-text court lookup. Live Matches does not know B's exact text for an idle court (fact 3).
    • A fixed geometry (5 + 3·(k − 1)). It is wrong for the team and dual-meet workbooks (fact 1).
    • GET …/courts. It would cost a Sheets read for no reader the snapshot doesn't already serve (D4).
    • Moving a match in one request. That is two cells, and a half-done write would leave the match on both courts or neither (D6).
