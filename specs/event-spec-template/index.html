    Event spec template¶

    Not a spec, and no build status. This is the starting point for every new event's spec, which is why it sits at the root of specs/ and not in a status folder. It is written from the seven event specs before it, Pickle for Sight to the UPAP 3rd Annual Tournament, and takes its shape from UPAP's, the first built in phases.

    An event spec is what lets someone with no other context build an event's pages and register it: every value, every edit, every check, written out. The procedure itself, which file to copy and which token means what, is the runbook in the site repo, _templates/CLAUDE.md. The spec does not repeat the runbook: it applies it to one event, with the event's own values, and adds the edits the runbook leaves to judgement (a re-skin, the board's colours, any engine change).

    There is one template for all three event types. Where they differ, the skeleton in Part 2 has a block for each: [Standard], [Team] and [Dual meet]. Keep the block for the event's type and delete the others.

    Part 1 — How to write an event spec¶

    1.1 Gather before you write¶

    Write nothing until you have all of this. Every fact in the spec comes from one of these sources, and the spec says which.

    • The workbook, read through the Sheets API, never from memory or a screenshot of it:
    • Title and Variables: the event name, date, facility, courts.
    • SCHEDULE and CSV: every match, numbered, with its time and court; the first serve; the slot length; any empty court.
    • STANDINGSCSV: every pair or team and every playoff seat.
    • ATTENDANCE: that its header is there.
    • [Team] Teams and MatchUps as well: the team names, rosters and pair numbers.
    • The generator version, from SAGE → Help. A format the master's generator does not build yet is a workbook nobody may regenerate; the spec says so in its operator tasks.
    • The facility name exactly as the workbook spells it. Live-sync setup compares it, with case.
    • The pubmat (the organiser's poster), if there is one: sample the palette from it, and the display font closest to its lettering. Measure the contrast of every pair the template uses (§1.5). With no pubmat the event keeps the house colours, as the Angeles City Employees Sportsfest did, and the spec has no re-skin.
    • The logo and the QR image. The logo is staged untracked in events/<event-key>/assets/ before the spec is written. The QR image usually follows later; the spec says what happens without it. The pubmat may sit beside them for reference and is never committed.
    • The precedent: the last event spec of the same type. Read what it did and what its status line says went wrong.
    • The owner's answers. Ask before writing the edits, not after: a changed answer moves every check that depends on it. The questions every event needs:
    Question Why it matters
    The short link (tinyurl.com/SAGEx…) and who makes the QR image {{QR_URL}}, the QR panel
    Attendance: desk links, console only, or none "attendance", whether attendance.html exists
    Score entry: scorer links, console only, or none "scoreEntry", whether scorer.html exists
    The category or bracket labels display in events.json, and every Standings check
    Which logo, if the organiser has more than one {{EVENT_LOGO}}
    Whether the staff pages (desk, scorer) take the event's colours or keep the house colours Phase 3's edits. House colours unless the owner says otherwise
    The build order, if not the default (§1.2) The phases
    The first serve, if the workbook and pubmat disagree The go-live time and every timing check
    With more than one day: how the board changes day (§1.3) An engine phase, or a push every evening of the event

    [Team] also: how teams are ranked (teamScoring, headToHeadQuotient), the pair labels (display.pairs), the playoff seats' labels before they're filled (display.seedLabels), team colours (display.teamColors), and whether lineups are hidden until shown (lineupReveal) or checked (lineupRules). [Dual meet] also: each club's code and name, and both clubs' logos.

    The answers go in the spec's Questions section, dated.

    1.2 Choose the phases¶

    Build in phases, each its own branch, its own checks and its own push. The default is three:

    Phase Builds Why here
    1 The schedule board and the event's events.json entry Registering the event lets the operators set up live sync and rehearse on the real board while the rest is built
    2 The Tournament Hub, with its logo (and the QR image, if it is in) The public page; the short link goes out after this
    3 Everything else: the desk page, the scorer page, the dry-run checklist, the QR image Staff pages, needed by the dry run

    The spec says what is live between phases, and what must not be used yet (Control Center's Open Tournament Hub leads to the 404 page until Phase 2; Issue desk link waits for Phase 3).

    An engine change comes first, as its own phase before the pages, when the event needs something lib/v1/ doesn't do (Ladies' Dink's tiebreaker game, lettered brackets). That phase:

    • Edits lib/v1/ compatibly only (_templates/CLAUDE.md §8): add, never remove or rename. One module may start using another's new export only in a later push, unless the export is in a module that did not exist before.
    • Writes the tests first and watches them fail.
    • If it touches the "played" or BYE rules, changes sage-tools-api's facilityCompletion.mjs in step, with its tests, a version bump and a changelog entry, and pushes the API first.
    • Lists the docs pages it changes (technical/site-engine.md, the features pages) and the workspace CLAUDE.md lines.

    Its skeleton is Part 3, inserted before the board's phase.

    One pass instead of phases only when the owner asks for it.

    1.3 Several facilities, or several days¶

    The skeleton is written for one day at one facility, as every event since the engine has been. The engine handles more (the board's Venue row, the Hub's day picker), but no event has used it yet: Pickle for Sight (one day, two facilities) and BKL Cup 2026 (five days × three facilities) both came before the engine. An event with more of either changes these parts of the spec (the section numbers are the skeleton's, in Part 2), and its spec checks every one of them in the dry run.

    Several facilities on a day. One workbook per facility per day.

    • Read every workbook (Part 1 §1.1), and list each facility in §1 with its courts and exact name.
    • Each workbook is its own entry in that day's facilities in §4.6: { name, sheetId }.
    • Match numbers must not repeat within a day, because a day's facilities merge into one snapshot. Each workbook numbers its own range with SAGE → Fill match numbers (1000s, 2000s). §8.1 checks that no two workbooks' CSV tabs share a number.
    • Court numbers run on across a day's facilities (Main 1–4, Annex 5–9), as each workbook's SCHEDULE sets them. The board then shows a Venue row, and ?venue=<facility> narrows it to one facility. There's nothing to configure, but §4.8 checks each ?venue=.
    • §8.2's sync setup runs once per workbook, each with its own facility name. Its confirm step lists every facility.
    • Desk and scorer links are issued per day, not per facility.
    • Appendix A's fixture writes every facility, with its own match-number range. Mission Control's checks in §4.8 name each facility.

    Several days. One days entry per day in §4.6, each day key unique across the whole file (<event-key>-day1, -day2, …), each with its own isLive and its own workbooks. The Hub's day picker comes from events.json, so the Hub needs nothing more. The board does: it shows exactly one day. Its DAY_KEY is fixed in schedule.html, it has no day picker, and Control Center's Open schedule opens that one file. Ask the owner which of these two to do, and record the answer in §9 and §10:

    1. Push the board every evening, with DAY_KEY set to the next day. No engine change, but every one of those pushes lands inside the 3-day freeze and needs its own go-ahead. §0.3 lists them with their dates.
    2. An engine phase first (Part 3) that lets the board choose its day, for example from a ?day= in its address or from today's date in events.json. Nothing is then pushed during the event. That phase changes lib/v1/apps/schedule-board.js and the templates' schedule.html compatibly, and Control Center's Open schedule link if the choice goes in the address.

    Each day's go-live, dry run (§8.5) and fixture state are then per day.

    1.4 Write every edit so it can't be misapplied¶

    • Anchor by text, never by line number. Each anchor is one line and occurs exactly once in its file; check that in the dry run. A range is given by its first and last line and the number of lines between them, so a wrong match is caught.
    • Give every replacement in full, in a fenced block, leading spaces included.
    • State each file's line endings. The checkout mixes them, and a search across lines can miss text that looks identical. Read them when writing, never from an older spec:
    git -C /d/Personal/SAGE/sage-match-control.github.io ls-files --eol _templates/

    The w/ column is the file on disk, which cp copies: w/crlf or w/lf. (i/ is what Git stores, LF either way.) The spec repeats what it found for each file it copies. - Never sed -i the site checkout: Git Bash's sed strips CR on this machine. A scripted edit is a Node script that detects the file's line ending, splits on it and joins on it. - Every check has its exact expected output: Prints nothing., Prints 8., the full line. Get each number by running the command in the dry run, never by counting by hand (UPAP's §5.4 counted a 19-line comment as 17). - Every phase starts with git status --short and the exact output it expects, unrelated untracked files included, so the implementer can tell an expected file from a stray one. - The events.json entry is added by a Node script, saved outside the repo, that refuses to run unless the file is in JSON.stringify(…, null, 2) form and the key is absent, adds the entry and prints the last two event keys. Before it, a grep -c shows the event and day keys are free: a duplicate day key fails the whole file's validation, and the API keeps the old copy. - A page cites the spec in its comments as sage-docs/docs/specs/.../<name>-spec.md (the workspace CLAUDE.md's rule). - A re-skin writes every colour through a var(--token), keeps the block headed lib/v1/css's house colours, through this page's tokens whole, and adds each re-skinned page to PAGES in _tests/unit/house-colours.test.mjs ([Team] a re-skinned Hub to TEAM_HUBS too). The token names stay --navy and --green whatever the colours are.

    1.5 Write the checks¶

    • Contrast, measured (WCAG AA: 4.5:1 for body text, 3:1 for large text, 24px or 19px bold), for each pair the pages use:
    Pair Carries Needs
    white on --navy the header, buttons, the board's top bar 4.5:1
    --navy on --green text on a green fill 4.5:1
    --ink and --ink-soft on --paper body text 4.5:1
    --green-dark on white accents Measured. Under 4.5:1 it is large text only
    --green on white fills Measured. Under 3:1 it is a fill only, never text

    The house palette already sits below two of those lines (--green-dark about 4.0:1, --green about 2.3:1), which is why the pages use them as they do. A re-skin's numbers go in the spec's design notes; a pair that falls short of its line is changed before the spec is handed over, not noted. - A fixture (Appendix A): a Node script that writes _fixtures/<event-key>/<state>.json and adds the event to _fixtures/config.json, shaped like the real workbook, with fixed scores so it prints the same line every run. It is never committed: the harness reads _fixtures/config.json, and an extra event changes its screenshots. Each phase removes it. [Team] writes pre, mid and finished; the others finished at least. - Browser checks at the widths that change the layout: 375px (phone), 1024px (the Hub's QR panel shows from 900px wide and can cover the hero's title just above that), 1280px, and 1440px for the board. UPAP's checks skipped 1024 and missed exactly that overlap. - Write each check as what is seen, with the fixture's real numbers and names, and list what is expected and not a bug (a 404 for qr.png before it's supplied).

    1.6 Dry-run the spec before handing it over¶

    Apply every edit exactly as written to a detached worktree of the site at the commit the spec names, never to the checkout:

    git -C /d/Personal/SAGE/sage-match-control.github.io worktree add --detach <scratch>/dry-run <sha>

    In it: every anchor matched once; each phase's unit tests (record the count); the fixture's printed line; every browser check; the events.json script on a copy of the file. Then remove the worktree (git worktree remove). The status line records the date, what was run and what was not (usually npm run verify's screenshot comparison, commits and pushes).

    If main has moved by the time a phase runs, re-dry-run that phase and update its counts.

    1.7 Deadline, pushes and filing¶

    • The deadline is the site freeze: no merge to the site's main within 3 days of the event. The status line names the last day a phase may land, and says that after it a push needs the owner's explicit go-ahead.
    • Every push and merge to main is the owner's yes in chat. Each phase ends in a Stop and ask step that says what the push will publish.
    • Filing: the spec starts in not-started/, named after the event (upap-3rd-annual-tournament-spec.md); the filename is unique across all four folders. It is added to the specs README's not-started list, not-started/README.md's table and mkdocs.yml's nav, with a MINOR docs version. It moves by the procedure in the specs README: to in-progress/ when its first phase is pushed, to implemented/ once the event has run. Each move is a MINOR docs version.
    • After the event, the spec's §8 turns live push off (LIVE_BASE_URL = '' in every page); archiving into events/archives/ is a later, separate step (_templates/CLAUDE.md §7).

    1.8 What an event spec does not do¶

    • Edit the workbook. That is the operators' list, §8 of the skeleton, written down so its constraints on the data are known.
    • Hold a secret. The sync secret is read from Cloud Run by whoever manages it, never pasted into the spec, chat or a document.
    • Tidy anything it doesn't need. "Don't rename, fix or tidy anything this spec doesn't mention" is one of its rules.

    Part 2 — The skeleton¶

    Copy everything inside the fence into not-started/<name>-spec.md. Replace every <…>; keep the type block that fits and delete the others; delete a section's guidance lines in italics once it's written. The section numbers assume no engine phase: with one, paste Part 3 in as §4, and the sections and phases after it move down by one.

    # Spec — <Event name>

> **Status: not started.** Written <YYYY-MM-DD> against `sage-match-control.github.io` at
> `<sha>`, `event-data`'s `config/events.json` at `<sha>`, and the event workbook as read that day
> through the Sheets API. The owner answered the open questions on <date>; the answers are in §9.
>
> **Built in <three> phases** (§0.3): <the schedule board with the event's `events.json` entry,
> then the Tournament Hub, then everything else>. Each phase is its own branch, its own checks and
> its own push.
>
> **Dry-run on <YYYY-MM-DD>.** Every edit of <§…> was applied to a detached worktree of the site
> at `<sha>`: every anchor matched exactly once. Appendix A's fixture was built and <the pages>
> were checked in a browser at 375px, 1024px, 1280px and 1440px; the checks in <§…> are what they
> showed. The site's unit tests passed after each phase's test change (<n>, then <n>). §4.6's
> `events.json` script was run on a copy of the file and printed what §4.6 expects. Not run in the
> dry run: <`npm run verify`'s screenshot comparison, and any commit or push>.
>
> **Deadline.** The event is on **<Weekday d Month YYYY>**. The site repo takes no merge within
> 3 days of an event, so **all phases reach the site's `main` by <Weekday d Month>**. After that,
> push only with the owner's explicit go-ahead.

Build the event pages for the **<Event name>**, <a one-day doubles tournament> run by **<the
organiser>** on **<date>** at **<venue, town>**, and register the event so the live system knows it.

The pages are copies of the site's <standard / team / dual-meet> event template, filled in for this
event and <re-skinned from the organiser's pubmat: …> <or: in the house colours>. <**No shared code
changes.** or: Phase 1 makes <n> compatible engine changes first: …>

## 0. Briefing — read all of it before you change anything

### 0.1 What you are working in

| Thing | Where | What it is |
| --- | --- | --- |
| **The site repo** | `D:\Personal\SAGE\sage-match-control.github.io` | A GitHub Pages site: hand-written HTML and native JavaScript modules, no build step, no framework. Pushing its `main` branch publishes it within a minute or two |
| **The engine** | `lib/v1/` in the site repo | Shared JavaScript and CSS that every event page loads. **You never edit it** <unless Phase 1 says so> |
| **The template** | `_templates/<type>-template/` (`index.html`, `schedule.html`) | The starting point for the event's pages: short HTML shells. **You copy it, never edit it** |
| **The `event-data` repo** | `D:\Personal\SAGE\event-data` | The shared data store. Its `config/events.json` registers every event. Its `main` also receives automatic sync commits, so always `git pull` right before you change it |
| **The workbook** | Google Sheet `<sheet id>` | Where the operators keep the schedule and scores. You don't touch it |
| **Control Center** | `tools/control-center.html` in the site repo | The operators' console. It lists every event in `events.json` |

Words this spec uses:

- **Fixture mode**: on `localhost` only, `?fixture=<state>` makes an engine page read
  `/_fixtures/config.json` and `/_fixtures/<event-key>/<state>.json` instead of the real data.
  Appendix A writes them. **The fixture is never committed.**
- **House colours**: the site's default palette (navy `#14263C`, green `#7CB92C`, off-white
  `#F6F7F2`). A **re-skin** replaces them in a page's `:root { … }` block, and
  `_tests/unit/house-colours.test.mjs` lists the re-skinned pages it checks.

> **[Standard]**
> - **Team code**: how the workbook names a pair, `<CATEGORY>_<n>`, e.g. `<B45HMD_2>`. Playoff
>   seats are `<CATEGORY>_F_1` (Final, seat 1), `<CATEGORY>_SF_2`, `<CATEGORY>_B_1` and so on.
> - **Category token**: the part before the first `_`: a **division** then an **event** (`MD`).

> **[Team]**
> - **Team code**: `<SIDE>_<PAIR>`. `SIDE` is a team letter in the bracket stage (`A`), or
>   `<STAGE>-<SLOT>` in a playoff (`QF-3`). `PAIR` is the pair number in the matchup.
> - **Matchup**: two teams' games against each other, sharing one `matchUp` value.

> **[Dual meet]**
> - **Team code**: `<CLUB>_<DIVISION><EVENT>_<n>`, e.g. `<PPA_B18MD_1>`. `<CLUB>` is one of the
>   two club codes, `<A>` and `<B>`.

### 0.2 Rules

- **Find edits by their anchor text, never by line number.** Every anchor is a single line and
  occurs exactly once in its file. If it isn't there, or is there more than once, **stop and
  report**. Don't guess and don't improvise a different edit.
- **Keep each file's line endings.** <List each copied file: CRLF or LF.> Where an edit replaces
  several lines, it names the first and the last line of the range and how many lines it spans.
  **Never use `sed -i`**: on this machine it strips the CR from every line.
- **Replacement text is given in full** in each fenced block. Copy it exactly, including leading
  spaces. Never retype a value from memory.
- **Use Git Bash** for every command. Python is not installed; Node is.
- **Edit only what the phase names:** files in `events/<event-key>/`, the list in
  `_tests/unit/house-colours.test.mjs`, and `config/events.json` in `event-data` <and, in
  Phase 1, the engine files it lists>. Don't edit `lib/`, `tools/`, `_templates/`, `_fixtures/`
  (except by running Appendix A, which you then undo) or any other event's folder. If something
  there seems to need a change, stop and report.
- **One phase at a time.** A phase starts only when the one before it is merged into `main` and
  pushed.
- **Commit** where a phase says *Commit*, with the message it gives, followed by a blank line and
  the attribution line your session's instructions give.
- **Never push, and never merge into `main`, without the owner's yes in chat.** Each phase ends at
  a **Stop and ask** step.
- **Never commit `assets/pubmat.*`.** It is reference only.
- Don't rename, "fix" or tidy anything this spec doesn't mention.

### 0.3 The phases

| Phase | Builds | Branch | Ends with |
| --- | --- | --- | --- |
| **1** (§4) | `events/<event-key>/schedule.html` and the event's entry in `event-data/config/events.json` | `<short>-board` | Push of the site **and** `event-data` |
| **2** (§5) | `events/<event-key>/index.html` and its logo | `<short>-hub` | Push of the site |
| **3** (§6) | <`attendance.html`, `scorer.html,`> the dry-run checklist, and the QR image if not already in | `<short>-rest` | Push of the site |

*With an engine phase, add a first row: Phase **1** (§4) builds the engine change (and
`sage-tools-api`'s, if it touches the played or BYE rules) on `<short>-engine`, and ends with a
push of the API, then the site. The rows below become Phases 2–4.*

What is live in between: <after Phase 1 the event is registered and the operators can set up live
sync (§8.2); **Open Tournament Hub** leads to "Page not found" until Phase 2; **Issue desk link**
waits for Phase 3; don't hand out the short link before Phase 2>.

*Several days with the board pushed each evening (§1.3 of the template): list those pushes here,
each with its date and its own go-ahead.*

### 0.4 Commands you will use in every phase

Unit tests (from the site repo root): `cd _tests && npm test; cd ..`

Full check (unit tests, then the comparison of `main` against your branch):
`cd _tests && npm run verify; cd ..`. If it says a Playwright browser is missing, run
`cd _tests && npx playwright install chromium; cd ..` once.

Serve the **repo root** on `localhost` for a browser check (Ctrl+C to stop):
`npx --yes http-server -p 8000 -c-1`
