    Spec — Push for attendance¶

    When someone is marked in at one desk, every other desk and Control Center's Attendance tab show it within a second or two, instead of within about 20 seconds. Pages stop polling: they read the list when they open, when they come back into view, when a nudge arrives, and when someone presses Refresh.

    The live Worker pushes a nudge, a message that says only this facility's list changed. It carries no names and no check-in state, so it can travel on a public socket. Each page that gets one re-reads the list from the API with its own token, as it does today. The API's reads from Google stay as they are.

    Status: implemented. Built in sage-tools-api 3.4.0 (the API and the live Worker), the site's lib/v1 (data/attendance-signal.js, the attendance view, the desk page, Control Center and the attendance template) and docs 2.12.0. Merged into main on 2026-10-13, with the site going out in three pushes (§1 D10). The Worker was deployed by hand on 2026-10-18. Written 2026-10-12 against sage-tools-api 3.3.0. It is tested against fakes and a local Worker; the owner's checks in §10.2 (P1–P7) and §6 step 4, which needs a Google workbook, had not run when it moved here. As built: a read of everything starts its 11 s follow-up when its reply arrives, not when it is sent (§5.2). A nudge that arrives while a page is hidden still gets its settle call 11 s later, which reads the list if the page is visible again by then (§5.1, D7). The people route's OpenAPI description and _templates/CLAUDE.md §7 (turn LIVE_BASE_URL off in a finished event's desk page too) were brought in line, though §0.2 does not list them.

    Builds on Live push delivery and Attendance for every event, whose D4 kept attendance off the live channel because the channel is public. This spec keeps that rule: nothing private goes over the socket. Read their §0 if a term here is unfamiliar.

    0. Read this first¶

    You are implementing this with no other context. Everything you need is in this page and the files it names. Read §0 to §2 in full before writing code, then do §3 to §6 in order. §10 is what to report when you finish.

    0.1 The system in one paragraph¶

    Each venue on each day has a Google Sheet (a facility workbook) with an ATTENDANCE tab. sage-tools-api (Node/Express on Cloud Run) reads and writes that tab as its service account. Desk staff open a desk link on a phone (the desk page, events/<key>/attendance.html) and operators use Control Center's Attendance tab. Both render lib/v1/views/attendance-view.js, which reads one facility's people with GET /v3/days/{day}/facilities/{facility}/people every 10 s while the page is visible, and marks someone with PUT …/people/{personKey}/attendance. The API caches the list for 10 s per workbook, per instance. Separately, the Cloudflare Worker sage-live holds one Durable Object per <event>/<day> that stores the day's public snapshot and pushes it to every open page over wss://…/live/<event>/<day>. Cloud Run publishes to it with a shared secret.

    0.3 Hard rules¶

    1. Commit to a feature branch, never to main. In each repo you change, create one branch (the same name in every repo, e.g. attendance-push, unless your session names one for you), commit there in small steps with clear messages, and push it. No pull request, no merge, no rebase of main, no force-push. The owner reviews the branches, merges and deploys. The workspace CLAUDE.md follows its own repo (sage-workspace) the same way.
    2. Never deploy the Worker (npx wrangler deploy), never call the production API or the production Worker, and never touch the real events.json. Run the Worker with npx wrangler dev; tests use fakes. Deploys are the owner's (§10.2).
    3. Write each test first and watch it fail, then make it pass. Never weaken or delete a test. No existing assertion should need to change; if one does, stop and report it.
    4. sage-tools-api: ESM .mjs, classes with constructor injection, no new dependency, no TypeScript, 4-space indent, double quotes, comments that say why. Obey the dependency rules in D:\Personal\SAGE\CLAUDE.md (enforced by test/unit/guards/dependency-rules.test.mjs): AttendanceService reaches the Worker only through the port injected in src/app.mjs.
    5. The Worker: plain JS, the style of live-worker/src/index.js. No new Durable Object class, so no new entry in wrangler.jsonc's migrations (§1 D2).
    6. Site: no new dependency, 2-space indent, single quotes, match the surrounding style. lib/v1 changes must be compatible (_templates/CLAUDE.md §8): add, never remove or rename. A browser can hold a 10-minute-old copy of one file beside a new copy of another, so the site change ships in three pushes (§1 D10). Write the code so each push is safe on its own.
    7. Find functions by name (grep -n "function name("), not by line number.
    8. Line endings: keep whatever each file has today (the files named here are LF).
    9. Cite this spec from code comments as sage-docs/docs/specs/.../attendance-push-spec.md, with literally ....
    10. Documentation is present tense: what the system does, not what changed.
    11. If the code contradicts this spec in a way that blocks you, stop and report it (§10). Don't work around it.

    1. Decisions (settled with the owner, 2026-10-12)¶

    # Decision
    D1 The nudge carries no data. The message is exactly {"type":"attendance","facility":"<name>"}. No person, key, name, state, time or count. A facility's name is already public in events.json. Pages re-read the list from the API with their own token
    D2 Its own object, not the day's snapshot channel. The Worker gives attendance a separate object, idFromName(\attendance:${event}/${day}`), of the **same**DayChannelclass (no migration). It stores nothing. Public viewers never receive a nudge, a desk never receives a snapshot, and a fault here can't reach the public feed. Event and day keys match[a-z0-9-], so theattendance:` prefix can't collide with a snapshot object's name
    D3 Two Worker routes. GET /attendance/<event>/<day> is the socket: Upgrade: websocket, the same Origin rule as /live, no secret, nothing sent on connect. POST /nudge/<event>/<day> with body { facility } needs X-Publish-Secret, broadcasts the D1 message to that object's sockets and answers 200 {clients}. A facility that isn't a 1–100 character string is 400
    D4 The API nudges after every write that changes the tab, and only then: a mark whose plan changed, a reconcile that created the tab, and a reconcile that wrote rows. One nudge per write, after the write and the cache drop
    D5 Best effort, awaited, short. The nudge is awaited before the response, because Cloud Run throttles CPU once a response is sent, with a 2-second timeout. A failure or timeout logs one warning and never changes the answer or throws
    D6 Nudges follow the environment, not the Sync method switch. The API nudges whenever LivePublisher.enabled (URL and secret set), whatever config.livePushOn says. With no polling (D8), a nudge is the only way other pages hear of a mark, and the switch is about how snapshots are delivered. After a failed nudge the service sends none for 60 s (per instance), so a Worker outage costs a mark at most one 2-second wait a minute
    D7 Pages coalesce. A nudge for a facility the page shows re-reads that facility only, at most once every 2 s (trailing). And once more 11 s after the last nudge, because another Cloud Run instance can hold a list up to 10 s old (PEOPLE_CACHE_MS), so the follow-up is never stale. Nudges for a facility the page doesn't show are ignored. While the page is hidden, nudges are ignored; the existing visibilitychange load catches up
    D8 No polling. The owner's call: no timer re-reads the list. A page reads it when it opens, when it comes back into view (visibilitychange: a phone that slept missed nudges), when its socket opens again after a drop (it missed nudges meanwhile), on a nudge (D7), and when someone presses the existing Refresh button. Each of those reads except a nudge's gets one follow-up read 11 s later (the owner's call, 2026-10-13): the read may be served from another instance's cache up to 10 s old, and a page that wasn't listening missed the nudges that would have corrected it. A newer such read restarts the 11 s; the follow-up itself schedules nothing, so this is never a poll. When the socket isn't open, the view says so in a line of its own: Live updates are off. Press Refresh to see marks from other devices.
    D9 Where it runs. The desk page (desks mode, from the template) and Control Center's Attendance tab. Off in fixture mode. A page with no Worker address gets no nudges and shows the D8 line. The finished events' inline desk pages are untouched and keep their own polling
    D10 Rollout order. (1) The Worker, deployed by hand, never within 3 days of an event. (2) The API: harmless before any page listens. (3) Site push A: attendance-signal.js (new) and attendance-view.js. (4) Site push B, at least 10 minutes after A: attendance-desk.js and tools/control-center.html start using them. (5) Site push C, at least 10 minutes after B: the attendance template passes the Worker address. A cached older attendance-desk.js refuses an unknown setting and renders nothing, which is why C waits
    D11 No read changes. GET …/people, its 10-second cache and its response stay exactly as they are. Google reads per facility don't go up
    D12 Versions. sage-tools-api 3.4.0 (minor: new behaviour, no new route). The Worker has no version; its README.md route table is its record

    2. Overview¶

    desk A marks someone
   PUT …/people/{personKey}/attendance  ──>  sage-tools-api  ──>  ATTENDANCE tab (write)
                                                  │  drop the list cache
                                                  │  POST /nudge/<event>/<day> {facility}   (2 s, best effort)
                                                  v
                                      sage-live: object "attendance:<event>/<day>"
                                                  │  {"type":"attendance","facility":"Gym"}
                         ┌────────────────────────┼─────────────────────────┐
                         v                        v                         v
                      desk A                   desk B                 Control Center
               (re-reads Gym:            (re-reads Gym now,        (re-reads Gym now,
                sees its own mark)        and again in 11 s)        and again in 11 s)
                         └──── GET …/facilities/Gym/people with its own token ───┘

    The cost is easy to see:

    • Google reads: unchanged. Every re-read goes through the existing 10 s cache.
    • API requests: none while nothing changes, instead of six a minute per page: a page that opens reads twice (now and 11 s later), then nothing until something happens. At most one re-read per 2 s per page during a burst of marks, plus one follow-up.
    • Worker: one nudge per write that changed the tab. Each nudge goes to that day's attendance sockets only.

    3. The Worker (sage-tools-api/live-worker/)¶

    3.1 src/index.js, fetch¶

    • Widen ROUTE to ^/(live|snapshot|publish|attendance|nudge)/(${KEY})/(${KEY})$.
    • Name the object by kind: attendance and nudge use `attendance:${event}/${day}`, the rest `${event}/${day}` as now. Same locationHint.
    • attendance: the same checks as live (426 without the upgrade header, 403 for a disallowed Origin), then stub.fetch(request). Today everything that isn't live falls through to the secret check, so widen that branch's condition to kind === "live" || kind === "attendance" rather than adding a second copy.
    • nudge: the same secret check as publish (401), POST only (else 405), then stub.fetch(request). That is one more || (kind === "nudge" && request.method === "POST") in the existing method check.

    3.2 DayChannel.fetch¶

    • attendance → a new #listen(): like #connect (create the pair, this.ctx.acceptWebSocket(server), answer 101) but send nothing.
    • nudge → a new #nudge(request). Parse the JSON body (400 bad json on failure). facility must be a string of 1–100 characters, else 400. Build JSON.stringify({ type: "attendance", facility }) and send it to every socket, as #publish does, ignoring a socket that throws. Answer Response.json({ clients }). Write nothing to storage.

    #connect, #read and #publish are unchanged. Comment the two new methods with this spec's path.

    3.3 smoke.mjs¶

    Add these as steps 7–12, after step 6 and before the existing ws.close(), on the same key (so the URLs are `${wsBase}/attendance/${key}` and `${base}/nudge/${key}`). ws is the step-2 /live socket, still open, its greeting already read. Add one helper beside nextMessage: noMessage(ws, ms), which resolves true if no message arrives within ms and false if one does.

    1. Open const att = new WebSocket(`${wsBase}/attendance/${key}`), wait for its open event, then: no message within 1 s (nothing is sent on connect).
    2. POST /nudge/${key} with the secret and { "facility": "Smoke Court" } answers 200 with clients ≥ 1. Start listening on both sockets before sending it.
    3. att receives exactly {"type":"attendance","facility":"Smoke Court"} within 2 s.
    4. ws (the /live socket) receives nothing within 2 s of that nudge.
    5. POST /nudge/${key} without the secret is 401; with the secret and { "facility": "" } it is 400; a GET with the secret is 405.
    6. att.send("ping") gets pong within 3 s. Then att.close().

    3.4 README.md¶

    Add the two routes to the route table, with the rules in D1–D3, in the README's own style.

    4. sage-tools-api¶

    4.1 LivePublisher.nudge (src/clients/LivePublisher.mjs)¶

    // One data-free nudge: "this facility's attendance list changed"
// (sage-docs/docs/specs/.../attendance-push-spec.md). -> { clients }.
// Throws on network errors, a 2-second timeout, 401, 400 and 5xx.
async nudge(event, day, facility) { … }

    POST {baseUrl}/nudge/{event}/{day} with X-Publish-Secret, Content-Type: application/json and the body { facility }. It times out after 2000 ms, not timeoutMs. Don't duplicate #request: give it a sixth, optional argument { what, timeoutMs } = {}, where what defaults to what it derives from the method today and timeoutMs to this.timeoutMs; read and publish keep calling it as they do. So nudge calls this.#request("POST", "nudge", event, day, { facility }, { what: "nudge", timeoutMs: 2000 }), throws await this.#failure("nudge", res) for any non-ok answer, and returns { clients: body.clients }. The messages are then live Worker nudge timed out after 2000ms and live Worker nudge failed: …. Unlike publish, it logs nothing on success (one line per mark would flood the log).

    4.3 AttendanceService (src/attendance/AttendanceService.mjs)¶

    • The constructor takes an optional signals (AttendanceSignals, default null). Type it in the JSDoc like the other dependencies.
    • The constructor stores this.signals = signals and this.nudgeFailedAt = 0 (ms since the epoch of the last failed nudge; per instance, in memory, like the caches).
    • A private async #nudge(event, day, facilityName):
    • Return at once unless this.signals?.enabled (D6). The registry's livePushOn is not consulted, so #nudge takes no config.
    • Return at once if this.now().getTime() - this.nudgeFailedAt < NUDGE_BACKOFF_MS (60 000, a constant beside PEOPLE_CACHE_MS).
    • Otherwise await this.signals.nudge(event, day, facilityName) inside try. On any error, set this.nudgeFailedAt = this.now().getTime(), log this.logger.warn(`attendance ${day}/${facilityName}: live nudge failed: ${err?.message ?? err}`) and return. Never throw.
    • mark: inside if (plan.changed), after updateValues and the cache delete, call await this.#nudge(event, day, facilityName) (event is already in scope from config.getDay(day)). The return value is unchanged.
    • #reconcileFacility: add event to its argument object, and pass it from both callers (reconcileAfterSync has it as an argument, reconcileDay from config.getDay(day)). Track whether this run called createAttendanceTab or called updateValues (only done when data.length > 0). If either, call await this.#nudge(event, day, name) once, after the race re-check and its logging, whether or not it raced (the tab changed either way), before the return. A skipped reconcile (same fingerprint) and a run with nothing to write send nothing. A reconcile after a sync runs inside RECONCILE_BUDGET_MS. A failing nudge adds at most 2 s, once a minute; if that ever tips a run past the budget, reconcileAfterSync logs and moves on as it already does. Change nothing there.

    5.1 lib/v1/data/attendance-signal.js (new) — push A¶

    // The attendance nudge (sage-docs/docs/specs/.../attendance-push-spec.md).
// One WebSocket per page to the Worker's attendance object for a day. A message says
// only which facility's list changed; the page re-reads it from the API.
import { LIVE_PING_MS, LIVE_PONG_TIMEOUT_MS, LIVE_RETRY_MAX_MS } from './live-channel.js';

export const ATTENDANCE_NUDGE_GAP_MS = 2000;   // at most one re-read per facility this often
export const ATTENDANCE_SETTLE_MS = 11000;     // sage-tools-api's PEOPLE_CACHE_MS (10 s) + 1 s

/**
 * @param {{ baseUrl: string, enabled: boolean, event: string, day: string,
 *           onChange: (facility: string) => void,
 *           onStatus?: (open: boolean) => void }} options
 * @returns {{ isOpen(): boolean, close(): void }}
 */
export function createAttendanceSignal(options){ … }

    These imports are of exports that already exist, and the file is new, so it's safe in push A.

    • The socket: connect to `${baseUrl}/attendance/${event}/${day}` (both URL-encoded) when enabled. Mirror createLiveChannel for upkeep: ping every LIVE_PING_MS, close if no pong within LIVE_PONG_TIMEOUT_MS, reconnect with the same backoff (1000 · 2^retries, capped at LIVE_RETRY_MAX_MS, plus up to 1 s of jitter). close() stops everything for good.
    • Messages: ignore pong and anything that isn't JSON with type === 'attendance' and a string facility.
    • Coalescing (D7), per facility:
    • Call onChange(facility) at once if the last call for that facility was at least ATTENDANCE_NUDGE_GAP_MS ago. Otherwise call it once when the gap ends.
    • After every nudge, (re)start that facility's settle timer: onChange(facility) again ATTENDANCE_SETTLE_MS after the last nudge.
    • Status: onStatus(true) when the socket opens; onStatus(false) when it closes or a connection attempt fails, once per change (not once per retry). The state starts unknown, so the first open or the first failure always reports. With enabled: false, never create a socket and call onStatus(false) once, on the next tick (setTimeout(…, 0), so the caller has its view by then).
    • isOpen() is !!ws && ws.readyState === WebSocket.OPEN, as in createLiveChannel.
    • After close(), no callback fires again: clear the ping, pong, retry, gap and settle timers, and detach the socket's handlers before closing it.
    • No pause on a hidden page: the view ignores nudges while hidden (§5.2), and a socket that died while a phone slept reconnects through the normal backoff.

    9. Alternatives considered (for the record; don't build these)¶

    Alternative Why not
    Push the list itself over the socket The socket is public (only Origin is checked, and that is trivially forged). Check-in state and shirt sizes are staff data
    An authenticated attendance socket, the Worker verifying desk and operator tokens The Worker would need the token keys, a second copy of AuthService's rules in another runtime, and their expiry rules kept in step. The data-free nudge needs none of it
    The nudge on the day's existing snapshot channel Every public viewer would receive every nudge, which also reveals when check-in activity happens. A fault in the new code would share an object with the public feed. It saves one socket per staff page
    Server-Sent Events from Cloud Run A long request per page keeps instances billed and busy, and a write on one instance can't reach a page connected to another
    Polling as a fallback (every 10 s, or 30 s while connected) The owner's call: no polling. The Refresh button, a re-read when the page comes back into view or reconnects, and the Live updates are off line cover the same gap
    A shorter poll More API requests with no fresher data: the 10 s cache sets the floor
    A ?since= on GET …/people that forces a fresh read A token holder could force a Google read per request; the 11 s follow-up gets the same freshness from the existing cache
